# Staleness is anchored to the default branch

A branch is stale when its work has landed. "Landed" needs somewhere to have landed *into*, and the original implementation used ambient `HEAD` — whatever branch the current worktree happened to be on. In a single-checkout repo that reads as "merged into main", because main is usually what you are standing on. In a repo with worktrees it is an accident of which directory you are in: committing in one worktree made every sibling worktree's branch look merged-and-behind, and a freshly created worktree branch was offered for deletion before it held a single commit.

Staleness is now judged against an **anchor**: the local default branch, or its remote counterpart when there is no local copy. When neither resolves, the merged rule stands down entirely and only a deleted upstream marks a branch stale — a repo with no discernible default branch gets no guesses.

## Consequences

- **Merged-ness alone cannot settle it.** Every branch listed by `--merged <anchor>` has its tip as its own merge-base with the anchor, so a branch freshly cut from the anchor is topologically identical to one whose commits were fast-forwarded onto it. The old code hid this behind a `has_unique_commits` helper whose "did it diverge?" test was unreachable for exactly this reason, leaving `tip == HEAD` — which fired on empty branches and missed genuinely merged ones.
- **Topology is not evidence; tracking is.** Two clauses remain, either of which suffices. A branch tracking the anchor's counterpart while *ahead* of it — as everything `wt` creates does — holds commits of its own, and being merged into the anchor is where they went. An untracked branch whose tip is *behind* the anchor's was merged locally and left behind. A branch cut from the anchor and never committed to satisfies neither, because it is never ahead of what it tracks.
- **Ambiguity resolves to silence, except where silence costs everything.** Where two branches with opposite histories present identical refs, the rule declines rather than guessing: guessing "stale" costs a branch someone was still using, guessing "not stale" costs a row in a prompt. The one place it guesses the other way is the untracked branch below, because there the alternative is not a missed row but a whole category — a branch that was never pushed has no deleted upstream coming to settle it later, so declining would mean never cleaning up local merges at all.
- **The ahead count is what separates work from emptiness.** After a fast-forward a branch's commits simply *are* the anchor's, and after a merge commit an empty branch cut from the merged topic sits off the anchor's first-parent chain exactly as the topic does — so neither the tip nor the shape of the history distinguishes work from none. Being ahead of the published anchor is the only remaining evidence, and it costs nothing: `upstream:track` is already read for the `-d` mirror. An earlier revision walked `rev-list --first-parent` as a third clause; it was removed once it proved to be reading noise, taking the rule's only expensive git call with it.
- **The upstream of a new worktree branch is load-bearing.** Telling a `wt` branch from a published one rests on which ref it tracks, so `worktree add` passes `--track` explicitly rather than relying on `branch.autoSetupMerge`, which users can turn off.
- **A branch published under a name of its own is exempt from both clauses.** Whether the anchor holds its work is a question about two *remote* branches, and no local ref answers it. Such a branch waits for its upstream to be deleted.
- **The ahead-count clause lapses once the anchor is pushed.** A `wt` branch's count falls to zero as soon as the anchor reaches its own upstream, and from then on nothing distinguishes it from a branch that never held a commit. It is not offered. This is the cost of the clause being the only honest signal there is, and it is why `wt` branches are worth cleaning up before pushing rather than after.
- **Three review rounds found the same false positive in three places.** Judging a published branch on tip equality; then, after that was removed, still letting it reach the first-parent walk; then the same walk offering an empty branch that tracked the anchor. Each was one expression of a single fact — an empty branch and a merged one present identical refs — and each was fixed locally rather than at the root. The rule is stated here as a property of what a branch *tracks* precisely so the next reviewer can check it in one place.
- **The `-d` mirror had to be corrected to match.** Judging landing by the ahead count surfaces branches merged into the anchor but not yet into its upstream, and `git branch -d` refuses exactly those — *"not yet merged to `refs/remotes/origin/main`, even though it is merged to HEAD"*. The mirror previously let merged-into-HEAD short-circuit, so those rows were marked risk-free and then failed to delete. Git's rule is an either/or: where an upstream exists it alone decides. Correcting it means such a branch now carries an `↑` marker, which per [ADR 0001](./0001-warned-means-forceable.md) is what licenses the `-D` that succeeds.
- **Untracked empty branches remain a known misfire.** Once the anchor moves past it, a hand-made `git branch --no-track` branch that was never committed to is indistinguishable from one merged locally. It is offered. Branches `git-switch wt` creates are immune, which is what the `--track` flag buys.
- **The cleanup prompt judges and deletes from the main worktree.** Staleness is measured against the default branch, but `git branch -d` measures against the HEAD it runs under. Asking from the current worktree would label a branch merged into the anchor "unmerged" whenever that worktree sits on something unrelated, and per [ADR 0001](./0001-warned-means-forceable.md) that marker would then license a force-delete. Running both in the main worktree keeps the marker honest.
- **Squash-merged branches are still the deleted upstream's job.** A branch merged by rebasing or squashing is not an ancestor of the anchor at all, so no merged rule can see it. That case belongs to `[gone]` after a pruning fetch, alongside the published branches above — between them the deleted upstream carries every branch whose fate the local refs cannot show.
