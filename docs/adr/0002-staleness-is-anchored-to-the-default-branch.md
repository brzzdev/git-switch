# Staleness is anchored to the default branch

A branch is stale when its work has landed. "Landed" needs somewhere to have landed *into*, and the original implementation used ambient `HEAD` — whatever branch the current worktree happened to be on. In a single-checkout repo that reads as "merged into main", because main is usually what you are standing on. In a repo with worktrees it is an accident of which directory you are in: committing in one worktree made every sibling worktree's branch look merged-and-behind, and a freshly created worktree branch was offered for deletion before it held a single commit.

Staleness is now judged against an **anchor**: the local default branch, or its remote counterpart when there is no local copy. When neither resolves, the merged rule stands down entirely and only a deleted upstream marks a branch stale — a repo with no discernible default branch gets no guesses.

## Consequences

- **Merged-ness alone cannot settle it.** Every branch listed by `--merged <anchor>` has its tip as its own merge-base with the anchor, so a branch freshly cut from the anchor is topologically identical to one whose commits were fast-forwarded onto it. The old code hid this behind a `has_unique_commits` helper whose "did it diverge?" test was unreachable for exactly this reason, leaving `tip == HEAD` — which fired on empty branches and missed genuinely merged ones.
- **Four clauses, any of which suffices.** A tip off the anchor's first-parent chain was merged *in*. A branch tracking its own counterpart whose tip *is* the anchor's had its published work fast-forwarded on. A branch tracking the anchor's counterpart while *ahead* of it — as everything `wt` creates does — holds commits of its own, and being merged into the anchor is where they went. An untracked branch whose tip is *behind* the anchor's was merged locally and left behind. A branch cut from the anchor and never committed to satisfies none: it tracks the anchor's counterpart but is never ahead of it, and it sits on the first-parent chain.
- **The ahead count is what separates work from emptiness.** For a branch tracking the anchor's counterpart, topology says nothing — after a fast-forward its commits *are* the anchor's first-parent chain. Being ahead of the published anchor is the only remaining evidence it ever held work, and it costs nothing: `upstream:track` is already read for the `-d` mirror.
- **The upstream of a new worktree branch is load-bearing.** Telling "never pushed" from "published and merged" rests on which ref a branch tracks, so `worktree add` passes `--track` explicitly rather than relying on `branch.autoSetupMerge`, which users can turn off.
- **A published branch fast-forwarded on, then left while the anchor moved, is missed.** It sits on the first-parent chain, its tip is no longer the anchor's, and it has an upstream — so no clause fires. This is not a gap that can be closed: it is character-for-character identical to a published branch that never held a commit at all, which must *not* be offered. The old rule missed it too. A pruning fetch catches it once the remote branch goes.
- **The ahead-count clause lapses once the anchor is pushed.** A `wt` branch merged into the anchor is offered until the anchor reaches its own upstream; after that the count falls to zero and the branch is again indistinguishable from an empty one. This is the same wall as above, reached from the other side.
- **The `-d` mirror had to be corrected to match.** Judging landing by the ahead count surfaces branches merged into the anchor but not yet into its upstream, and `git branch -d` refuses exactly those — *"not yet merged to `refs/remotes/origin/main`, even though it is merged to HEAD"*. The mirror previously let merged-into-HEAD short-circuit, so those rows were marked risk-free and then failed to delete. Git's rule is an either/or: where an upstream exists it alone decides. Correcting it means such a branch now carries an `↑` marker, which per [ADR 0001](./0001-warned-means-forceable.md) is what licenses the `-D` that succeeds.
- **Untracked empty branches remain a known misfire.** Once the anchor moves past it, a hand-made `git branch --no-track` branch that was never committed to is indistinguishable from one merged locally. It is offered. Branches `git-switch wt` creates are immune, which is what the `--track` flag buys.
- **The cleanup prompt judges and deletes from the main worktree.** Staleness is measured against the default branch, but `git branch -d` measures against the HEAD it runs under. Asking from the current worktree would label a branch merged into the anchor "unmerged" whenever that worktree sits on something unrelated, and per [ADR 0001](./0001-warned-means-forceable.md) that marker would then license a force-delete. Running both in the main worktree keeps the marker honest.
- **Squash-merged branches are still the deleted upstream's job.** A branch merged by rebasing or squashing is not an ancestor of the anchor at all, so no merged rule can see it. That case belongs to `[gone]` after a pruning fetch, and the two rules divide the work between them.
