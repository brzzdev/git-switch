# Staleness is anchored to the main line

A branch is stale when its work has landed. "Landed" needs somewhere to have landed *into*, and the original implementation used ambient `HEAD` — whatever branch the current worktree happened to be on. In a single-checkout repo that reads as "merged into main", because main is usually what you are standing on. In a repo with worktrees it is an accident of which directory you are in: committing in one worktree made every sibling worktree's branch look merged-and-behind, and a freshly created worktree branch was offered for deletion before it held a single commit.

Staleness is now judged against an **anchor**: the local default branch, or its remote counterpart when there is no local copy. When neither resolves, the merged rule stands down entirely and only a deleted upstream marks a branch stale — a repo with no discernible main line gets no guesses.

## Consequences

- **Merged-ness alone cannot settle it.** Every branch listed by `--merged <anchor>` has its tip as its own merge-base with the anchor, so a branch freshly cut from the main line is topologically identical to one whose commits were fast-forwarded onto it. The old code hid this behind a `has_unique_commits` helper whose "did it diverge?" test was unreachable for exactly this reason, leaving `tip == HEAD` — which fired on empty branches and missed genuinely merged ones.
- **Three clauses, any of which suffices.** A tip off the anchor's first-parent chain was merged *in*. A branch tracking its own counterpart whose tip *is* the anchor's had its published work fast-forwarded on. An untracked branch whose tip is *behind* the anchor's was merged locally and left behind. A branch cut from the main line and never committed to satisfies none: it tracks the anchor's counterpart, not its own, and sits on the first-parent chain.
- **The upstream of a new worktree branch is load-bearing.** Telling "never pushed" from "published and merged" rests on which ref a branch tracks, so `worktree add` passes `--track` explicitly rather than relying on `branch.autoSetupMerge`, which users can turn off.
- **Untracked empty branches remain a known misfire.** Once the anchor moves past it, a hand-made `git branch --no-track` branch that was never committed to is indistinguishable from one merged locally. It is offered. Branches `git-switch wt` creates are immune, which is what the `--track` flag buys.
- **The cleanup prompt judges and deletes from the main worktree.** Staleness is measured against the default branch, but `git branch -d` measures against the HEAD it runs under. Asking from the current worktree would label a branch merged into the main line "unmerged" whenever that worktree sits on something unrelated, and per [ADR 0001](./0001-warned-means-forceable.md) that marker would then license a force-delete. Running both in the main worktree keeps the marker honest.
- **Squash-merged branches are still the deleted upstream's job.** A branch merged by rebasing or squashing is not an ancestor of the anchor at all, so no merged rule can see it. That case belongs to `[gone]` after a pruning fetch, and the two rules divide the work between them.
